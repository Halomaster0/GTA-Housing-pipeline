# Security Policy

## Scope

GTA Housing Pipeline is a public, read-only analytics project built over open municipal and government data (building permits, development applications, zoning, housing starts, census data). There is no user authentication, no billing, no multi-tenancy, and no user-submitted data of any kind — see the README's "What it doesn't do" section for the full list of non-goals.

**In scope:**
- Vulnerabilities in this repository's own code (ingestion, transform, API, web app, evaluation harness)
- Exposure of secrets, keys, or credentials in the codebase or git history
- SQL injection or unsafe query execution in the AI query layer or the API
- Prompt-injection vectors that could cause the system to take an unintended action, exfiltrate data it shouldn't, or misrepresent what the underlying data says
- Denial-of-service or cost-exhaustion vectors against the public `/ask` endpoint or any public API route
- Dependency vulnerabilities in pinned packages

**Out of scope:**
- Vulnerabilities in the upstream municipal or government data portals themselves — report those to the relevant portal operator, not here
- Findings from the accuracy of open-data source content — this project reports what municipalities publish and marks known gaps; it does not audit their data
- Social engineering, physical security, or anything not related to this codebase or its deployed services

## Reporting a vulnerability

Please report security issues using **GitHub's private security advisory feature** for this repository (Security tab → "Report a vulnerability"). This keeps the report private until a fix is available while still using the repository's own infrastructure — do not email a report to a personal address, since none is published for this purpose.

Include, where relevant: what you found, the affected file or endpoint, a reproduction path, and the potential impact. This project has no dedicated security team; response is best-effort, but reports will not be ignored.

## Secret-in-history procedure

If a secret, key, token, or credential is ever found committed to this repository's git history — no exceptions for "it was rotated already" or "it was only there briefly":

1. **Rotate the credential immediately**, before doing anything else. Treat it as compromised from the moment it was committed, regardless of whether it appears to have been accessed.
2. **Rewrite git history** to remove it, in the same session, before the next push to the remote.
3. Both steps happen together, same session. Rotation without a history rewrite leaves the exposed value discoverable forever in a public repo; a history rewrite without rotation is meaningless if the value was ever pushed.
4. Document what happened and when in the relevant PR or issue, without re-exposing the secret itself.

## Prompt-injection posture

Free-text fields in the underlying municipal open data (application notes, permit descriptions, and similar) flow into prompts as part of the AI query layer's retrieval and generation steps. That text is public, municipally sourced, and **not trusted input** — it is written by third parties this project has no relationship with and no control over.

Mitigations:
- Retrieved free-text content is treated as data to be summarized or searched, never as instructions the model should follow.
- The system's actions are constrained by design: the model can retrieve rows and draft an answer, but cannot take any action beyond that (no writes, no external calls, no state changes) regardless of what retrieved text contains.
- Every answer the system produces is checked against the rows actually retrieved for that query (a faithfulness check) before being returned, which also bounds the damage an injected instruction embedded in source text could do to the final answer.
- This is evaluated as an explicit part of the eval harness, not assumed to be handled.

## SQL execution posture

Any SQL generated by the language model layer:
- **Executes read-only**, against a database role with no write, DDL, or DML privileges of any kind.
- **Runs against an allowlisted schema** — only the gold-layer tables the query layer is meant to expose are reachable; nothing else is queryable through this path.
- **Is parsed and validated before execution** — generated SQL is checked against the allowlist and basic structural expectations before it ever reaches the database, not executed blind on the assumption that the model behaved.

No LLM-generated SQL executes DDL or DML against this project's data, under any circumstance.

## Supported versions

This project does not yet have tagged releases. Security reports are evaluated against the current state of the default branch.
